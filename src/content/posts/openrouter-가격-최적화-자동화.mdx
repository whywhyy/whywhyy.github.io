[오픈라우터 설정 팁](/posts/openrouter-가격-최적화-설정팁/) 글을 쓰고 나서, OpenRouter가 라우팅 알고리즘을 재설계했다는 공지를 읽었다. 읽고 나니 내 설정이 **새 라우터를 스스로 끄고 있었다.** 이 글은 그걸 바로잡은 과정과, 그 위에 얹은 검증 자동화에 대한 기록이다.

## 왜 자동화가 필요했나

`sort: "price"`를 켜면 오픈라우터가 "가장 싼" 제공자를 골라준다. 문제는 **그 "싼"이 내 사용 패턴 기준인지** 확신이 없다는 것이다.

세션 로그를 집계해보니 패턴이 이랬다.

```
프롬프트 토큰 중 캐시 읽기   94%
출력 토큰 비중               0.12%
```

프롬프트의 94%가 캐시에서 읽힌다. 즉 **입력 단가보다 캐시 단가가 비용을 지배한다.** 그런데 가격 정렬은 그걸 고려하지 않는다. 실제로 그 정렬이 고른 제공자는, 내 믹스로 재계산하면 최적이 아니었다.

## 판단 기준을 순서로 정리하면

| 순위 | 요소 | 이유 |
|---|---|---|
| 1 | 캐시 동작 | 프롬프트의 94%가 캐시. 안 되면 비용 5배 |
| 2 | 파라미터 지원 | `require_parameters`를 통과해야 요청이 도달함 |
| 3 | 제공자 신뢰성 | 죽으면 요청 실패 |
| 4 | 품질 | 양자화(fp8/fp4), 구조화 출력 |
| 5 | 가격 | 캐시가 지배하면 입력가 차이는 상쇄 |

**2번을 처음엔 몰랐다.** 뒤에 나오는 실패가 여기서 나온다.

## 만든 것 — 5개

전부 스크립트 페이로드다. **OpenClaw 모델 턴을 쓰지 않으므로** 에이전트 대화 토큰은 0이다.

| 주기 | 하는 일 |
|---|---|
| 30분 | 잔액·키 잔여·키 만료 |
| 매일 09:10 | status·uptime·캐시·품질·풀 위험 |
| 매일 09:20 | 토큰 믹스 재계산, 허용 풀 내 비용 비교, 히트율 |
| 매일 09:30 | 설정 변경 효과 검증 |
| 매주 월 09:40 | 전체 엔드포인트 탐색 + 교체 권고 |

정상일 때는 다섯 개 모두 침묵한다. 알림은 채팅과 폰으로 간다.

## 프로브 설계 — 여기서 세 번 틀렸다

값을 재려면 실제 모델을 호출해야 한다. 그 설계에서 세 번 오판했다.

**① 캐시 프리픽스가 너무 짧았다**

처음엔 약 600토큰으로 캐시를 확인했다. Morph가 `cached=0`을 뱉어서 "캐시 안 됨"으로 판정했다. 2,000토큰으로 늘리니 정상 적중했다.

```
600토큰 프리픽스   cached 0
2,000토큰 프리픽스  cached 1024  ✅
```

캐시 최소 길이 아래에서는 **멀쩡한 제공자가 탈락**한다.

**② 품질 프로브가 잘렸다**

구조화 JSON을 요구할 때 `max_tokens: 80`으로 보냈더니, 추론 토큰이 그걸 다 먹고 본문이 비었다. 원문을 직접 보니 정상 JSON이었다. 300으로 올리고 코드펜스 허용을 추가했다.

**③ 실제 요청과 조건이 달랐다**

이게 제일 큰 실수였다. 프로브는 파라미터를 최소로 보냈는데, 실제 에이전트 요청에는 `presence_penalty`, `seed`가 붙는다. 그래서 "모든 축에서 우위"라고 판정한 제공자가 실트래픽에서는 **아예 후보에서 제외**됐다.

```
내 요청: tools + presence_penalty + seed
해당 제공자 지원: tools만
→ require_parameters가 라우팅 전에 제외
```

**측정 조건이 실제 조건과 같은지**를 확인하지 않으면, 정밀해 보이는 숫자가 전부 무의미해진다.

## 변경이 도움이 됐는지 어떻게 아나

설정을 바꾸고 "나아졌겠지"로 끝내면 안 된다. 그래서 설정 해시를 감시하다가, 바뀌면 직전 7일 기준선(`$/1M 토큰`)을 저장하고 3일 뒤부터 비교한다. 15% 이상 움직이면 개선인지 악화인지 알린다.

첫 측정에서 예상과 반대로 **비용이 9% 올라 있었다.**

```
변경 전   $0.0185/1M
변경 후   $0.0202/1M
```

이유는 캐시 비중이었다. 캐시가 92%일 때 나머지 8%의 신규 입력가가 승부를 가른다. 새 제공자는 캐시 단가가 40% 쌌지만 신규 입력가는 3.5배 비쌌다. **내가 세운 지표가 틀렸던 것**이고, 그래서 이 장치가 필요하다.

## 알림에는 권고와 실행 명령이 같이 온다

탐색 결과가 조건을 넘으면(현재 1순위보다 15% 이상 저렴 + 모든 프로브 통과) 이렇게 붙는다.

```
권고: StreamLake를 1순위로 (현재 Morph)
openclaw config patch --stdin <<'EOF'
{"models":{"providers":{"openrouter":{"params":{"provider":{"order":[...]}}}}}}
EOF
```

**자동 적용은 하지 않는다.** 지표는 매일 흔들리고(어떤 제공자는 어제 캐시 미적중, 오늘 적중), 제공자를 바꾸면 캐시가 비어 최소 1턴은 전액 과금이다. 판단은 사람이, 실행만 복붙 한 번으로 줄이는 게 지금의 균형이다.

## 비용은 거의 0이다

두 층으로 나뉜다.

- **OpenClaw 모델 턴은 쓰지 않는다** — 스크립트 페이로드라 에이전트 대화를 시작하지 않는다.
- **프로브는 실제 모델을 호출한다** — 캐시·품질·처리량을 재려면 요청을 보내야 한다.

| 프로브 | 요청 | 토큰 |
|---|---|---|
| 캐시 (2,000토큰 × 2회) | 2 | 약 4,000 |
| 품질 (JSON) | 1 | 약 100 |
| 처리량 (스트리밍 400토큰) | 1 | 약 400 |

하루 4요청, 약 4,500토큰. 입력가 $0.04/M 기준으로 **하루 $0.0002, 월 $0.006** 수준이다.

즉 "감시하느라 비용이 드는" 구조가 아니라 **감시 비용이 반올림 오차인** 구조다.

## 한계

로컬 집계는 청구서와 완전히 일치하지 않는다. 30일 기준 로컬 합계가 실제 청구액의 **83%** 수준이었다. 유틸리티 호출이나 중단된 시도가 로컬에 덜 기록되기 때문이다. 그래서 이 자동화는 **상대 비교**에는 쓸 수 있지만, **절대 금액**은 오픈라우터 쪽 숫자를 봐야 한다.

## 라우팅 재설계 — order를 빼고 only만 남기기

### 무엇이 바뀌었나

예전 기본 라우터는 사실상 **입력 토큰 가격**만 봤다. 싼 곳이 이기고, 실패하면 다음 싼 곳으로 넘어갔다. 그 방식의 부작용을 OpenRouter 스스로 이렇게 정리했다.

> Cheap won even when it was bad. … a provider could keep traffic share with weird pricing cocktails like listing an artificially low input price and then making back the difference with overpriced cached or completion tokens.

새 라우터는 요청마다 **"좋은 답 하나에 얼마가 드는가"** 를 계산한다.

| 신호 | 내용 |
|---|---|
| effective price | 실제 캐시 적중률과 실제 입출력 비율을 반영한 가격 |
| throughput | 초당 출력 토큰 |
| TTFT | 첫 토큰까지 걸리는 시간 |
| rate limit | 429를 얼마나 자주 내는지 |
| reliability | 제공자 귀책 실패율 |
| quality | 툴 호출이 제대로 돌아오는지 |

공개된 실험(2,400만 요청, 1주) 결과는 이렇다.

```
TTFT p50        1,007ms → 837ms   (−16.9%)
throughput p50  62.4 → 72.6 tok/s (+16.3%)
429 발생         7.1% → 3.8%      (−46%)
비용             +6.0%
```

**조금 더 내고 훨씬 빠르고 안정적으로** 가는 쪽을 기본값으로 택한 것이다.

### 내 설정이 그걸 끄고 있었다

문제는 이 문장이었다.

> Requests that set `provider.order` **bypass the new routing logic**, with providers ordered as specified. Setting `provider.only` or `provider.ignore` will use the new algorithm to select from the remaining providers.

나는 `order`에 다섯 곳을 나열해뒀다. 즉 **새 라우터를 우회하고, 내가 정한 순서대로만** 가게 만든 상태였다. 게다가 캐싱 문서에는 이런 문장도 있었다.

> Sticky routing is **not used when you specify a manual provider order** via `provider.order`.

sticky routing은 대화를 같은 제공자에 고정해 프롬프트 캐시를 유지하는 기능이다. 내 워크로드는 프롬프트의 94%가 캐시라서, 이걸 끄는 손실이 작지 않다.

### 바꾼 설정

```json5
provider: {
  only: ["Morph", "DeepInfra", "Cloudflare"],
  allow_fallbacks:    true,
  require_parameters: true,
  data_collection:    "deny",
}
```

`order`를 지우고 `only`만 남겼다. 후보는 내가 검증한 곳으로 제한하되, 그 안에서 고르는 일은 알고리즘에 맡긴다.

### 실제로 어떻게 도나

같은 요청을 반복해봤다.

```
session 없이   Morph → DeepInfra → Morph
session 고정   DeepInfra → DeepInfra → DeepInfra
```

`session_id`를 주면 한 곳에 고정된다. 안 주면 메시지 해시로 대화를 식별해 sticky가 동작한다. 즉 **대화 단위로는 캐시가 유지되고, 대화가 다르면 부하가 분산된다.**

### 부작용 — 후보가 셋으로 줄었다

`require_parameters`를 켜면 요청에 포함된 파라미터를 전부 지원하는 제공자만 남는다. 내 요청에는 `presence_penalty`와 `seed`가 들어간다.

```
PrimeIntellect  미지원: presence_penalty, seed  → 탈락
Together        미지원: seed                    → 탈락
Morph / DeepInfra / Cloudflare  전부 지원        → 생존
```

목록에 다섯 곳을 넣어도 **실제로 서비스할 수 있는 곳은 세 곳**이었다. 그래서 `only`도 셋으로 줄였다. 후보 수를 부풀려두면 "다섯 곳 중 하나가 살아남겠지"라는 착각만 생긴다.

### 429는 장애가 아니다

점검 중에 Cloudflare가 429를 냈다.

```
429 Provider returned error
"deepseek/deepseek-v4.1-flash-1017 is temporarily rate-limited upstream"
```

이걸 장애로 알리면 오탐이다. **일시적 레이트리밋은 정상 동작의 일부**이고, 새 라우터는 429를 비용으로 계산해 자연히 트래픽을 옮긴다. 그래서 감시 스크립트에서 429는 알림에서 빼고 로그로만 남기게 고쳤다.

### 비용은 어떻게 되나

새 라우터는 가격만 보지 않으므로 **비용이 조금 오를 수 있다.** OpenRouter 실험에서 6%였다.

다만 내 워크로드는 캐시가 94%이고, 새 라우터의 effective price는 **실제 캐시 적중률을 반영**한다. 즉 캐시를 잘 맞히는 제공자가 가격에서도 유리하게 계산된다. 6%보다 적게 오를 가능성이 있다.

3일 뒤 자동 비교가 판정한다. 기준선은 `$0.0146/1M`이다.

## 결론

- 기본 라우터는 이제 **가격 + 속도 + 신뢰성 + 품질**을 함께 본다. `order`는 그걸 우회하고 sticky routing까지 끈다.
- `only`는 필터로만 쓰고, 선택은 알고리즘에 맡기는 게 맞다.
- `require_parameters`를 켜면 후보가 크게 줄어든다. 정확성의 대가다.
- 429는 장애가 아니라 라우터가 처리할 신호다.
- 자동화는 이 판단이 **여전히 유효한지** 감시한다. 프로브 설계에서 세 번 틀렸고, 그때마다 측정 방법이 교정됐다.
