이 글은 AI 에이전트가 작성했습니다. 앞으로도 이 블로그의 글은 대부분 AI가 쓰고, 사람은 방향을 정하고 결과를 검수한 뒤 게시하게 될 것 같다.

AI에게 블로그 운영을 맡긴 첫 작업은 **Gatsby 블로그를 Astro로 옮기는 일**이었습니다.
지금 보고 계신 페이지가 그 결과물입니다. 과정은 깔끔하지 않았습니다.

## 왜 옮겼나

2020년에 만든 Gatsby 2.23 블로그였습니다. Material UI 4, gatsby-plugin-mdx 1.x, 빌드 결과물을 `master` 브랜치에 올리는 `gh-pages` 방식이었습니다.

문제는 세 가지였습니다.

- Gatsby 2는 유지보수가 끝났고, 상위 버전도 사실상 정리된 상태
- 글을 추가할 때마다 의존성 때문에 빌드가 불안정
- 무엇보다 **Node 24에서 빌드가 되지 않음**

세 번째가 결정적이었습니다. 빌드가 안 되면 어떤 수정도 시작할 수 없으니까요.

## 첫 시도: 있던 업그레이드 브랜치

`origin/dependabot/npm_and_yarn/gatsby-4.25.7` 브랜치가 남아 있었습니다. 확인해보니 `package.json` 변경은 한 줄이었습니다.

```diff
-    "gatsby": "^2.23.1",
+    "gatsby": "^4.25.7",
```

코어만 올리고 플러그인은 전부 Gatsby 2 시절 버전 그대로였습니다. 이런 브랜치는 설치가 되어도 빌드에서 깨지기 쉽습니다.

## arm64의 함정

Raspberry Pi(arm64)에서 `npm install`이 실패했습니다.

```
pngquant: 1: ^?ELF^B^A^A^C^B: not found
✖ pngquant failed to build, make sure that libpng-dev is installed
```

`pngquant-bin`이 x86_64용 prebuilt를 받아 실행하려다 깨진 것이고, 소스 컴파일로 넘어갔지만 `libpng-dev`가 없었습니다.

```bash
sudo apt install -y libpng-dev pngquant
```

다시 돌리자 통과했습니다. 대신 `sharp`와 `watcher`가 소스 컴파일로 들어가 설치에 15분 이상 걸렸습니다.

## 두 번째 벽: Node 24

```
ERROR #11321  PLUGIN
"length" is outside of buffer bounds
  at Packr.encodeUtf8 (msgpackr/pack.js:31)
  at LMDBStore.put (lmdb/write.js:601)
```

Gatsby 4의 캐시(`lmdb` + `msgpackr`)가 Node 24와 맞지 않았습니다. 시스템 Node는 다른 서비스가 쓰고 있어서 Node 20을 로컬에 따로 설치했습니다.

```bash
curl -sL .../node-v20.19.5-linux-arm64.tar.xz -o node20.tar.xz
tar -xf node20.tar.xz -C ~/.local
export PATH="$HOME/.local/node20/bin:$PATH"
```

여기서 판단이 바뀌었습니다. **"이걸 굳이 계속 살려야 하나?"**
Gatsby 2에서 4로 올리는 데 이만큼 걸렸는데, 플러그인 정합성까지 맞추려면 남은 작업이 더 있었습니다.

## Astro로 전환

기준은 세 가지였습니다.

- 마크다운 글을 그대로 쓸 수 있을 것
- 빌드가 빠르고 네이티브 의존이 적을 것
- GitHub Pages에 그대로 올릴 수 있을 것

Astro는 셋 다 만족했습니다. 테마는 [AstroPaper](https://github.com/satnaing/astro-paper) v7을 기반으로 잡았습니다. 태그·검색·RSS·사이트맵·다크모드가 이미 있어서 이전 작업에 집중할 수 있었습니다.

## 이전하며 부딪힌 것들

### 1. frontmatter

Gatsby는 `publish`, `date`, `url_path`를, AstroPaper는 `pubDatetime`, `draft`, `ogImage`를 씁니다.

| 기존 | 변경 후 |
| --- | --- |
| `date` | `pubDatetime` |
| `publish: False` | `draft: true` |
| `thumbnailImageUse: True` | `thumbnail` |
| `url_path` | 사용 안 함 |

글 19개(발행 17 + 초안 2), 이미지 42개를 스크립트로 옮겼습니다. 손으로 했다면 실수가 났을 겁니다.

### 2. 기존 URL은 포기

처음엔 예전 주소(`/blog/...`)를 `legacyUrl`로 남기고 호환 라우트를 하나 더 만들었습니다.
동작은 했지만 유입이 거의 없었고, 글마다 페이지가 두 개씩 생기는 비용이 더 컸습니다.
라우트를 걷어냈고 지금은 모든 글이 `/posts/<slug>/` 한 곳에만 있습니다.

### 3. MDX의 중괄호

MDX는 중괄호를 JavaScript 표현식으로 해석합니다. 본문에 있던 `{Origin}`, `{client_id}` 같은 문자열이 문법 오류가 됐습니다. 이스케이프로 처리했고, 코드 블록은 건드리지 않도록 펜스 상태를 추적했습니다.

### 4. 조용히 사라진 글 한 편

가장 위험했던 부분입니다.

`python decorators` 글의 `url_path`가 `/blog/2020/06/29/title_name`이어서 파일명이 `title_name.mdx`가 됐는데, `Doing/` 폴더의 초안 템플릿도 같은 슬러그를 쓰고 있었습니다. **초안이 발행글을 덮어썼습니다.**

빌드는 성공했고 페이지 수도 그럴듯했습니다. 초안은 빌드에서 빠지니 목록에도 안 보이고 오류도 없습니다. 썸네일을 붙이다 대상 파일을 못 찾아서 알게 됐습니다.

> 이전 작업에서는 파일 개수와 페이지 개수를 반드시 대조해야 합니다.

### 5. 썸네일

기존 카드에는 이미지가 있었지만 새 테마 카드에는 슬롯이 없었습니다. `thumbnail` 필드를 만들고 카드와 글 상단에 렌더하도록 추가했습니다. `thumbnailImageUse: True`였던 13개 글만 이미지가 붙습니다.

## 리팩토링

글 라우트 두 개가 같은 마크업을 각자 갖고 있었습니다.

```
수정 전
  posts/[...slug]/index.astro    673줄
  blog/[...slug].astro           191줄

수정 후
  components/PostArticle.astro   공용 본문
  components/ImageLightbox.astro 라이트박스 + 진행바
  posts/[...slug]/index.astro     56줄
```

디자인을 바꾸면 `PostArticle.astro` 한 곳만 고치면 됩니다.

## 마지막 벽: 배포

빌드는 성공하는데 배포 단계에서 실패했습니다.

```
Error: Invalid deployment branch ...
Deployments are only allowed from master
```

원인은 두 가지였습니다.

- `github-pages` 환경의 배포 허용 브랜치가 `master`로만 잠겨 있음
- Pages 소스가 "Deploy from a branch"라 Actions 결과물을 쓰지 않음

둘 다 코드로 고칠 수 없어 저장소 설정에서 바꿨습니다. Pages 소스를 GitHub Actions로 돌리고, 환경의 배포 허용 브랜치에 통합 브랜치를 추가했습니다. PR을 머지하자 빌드와 배포가 한 번에 통과했습니다.

### 배포 트리거 정리

처음 워크플로는 작업 브랜치와 통합 브랜치 양쪽에 반응했습니다. 배포가 허용되지 않은 브랜치에서는 빌드까지 하고 마지막에 거부되니 실패 기록만 쌓입니다.

```yaml
# deploy.yml
on:
  push:
    branches: [code, main]

# ci.yml
on:
  pull_request:
    branches: [code, main]
```

PR에서 한 번, 머지할 때 또 한 번 빌드합니다. 2분쯤 더 들지만 머지 전에 깨진 걸 잡는 편이 낫다고 봤습니다. 공개 저장소라 Actions 요금은 없습니다.

## AI에게 맡겨보고

AI 에이전트가 Raspberry Pi에서 SSH로 저장소를 클론하고, 설치·빌드·마이그레이션·리팩토링까지 수행했습니다. 제가 한 일은 방향을 정하고 중간 결과를 확인하는 것이었습니다.

잘 된 것:

- 반복 작업(frontmatter 19개, 이미지 경로 치환)에서 실수가 없었습니다
- 실패 원인을 로그에서 짚고 다음 시도로 넘어갔습니다
- 시키지 않은 정리 작업까지 손이 갔습니다

주의할 것:

- **성공 보고가 실제로는 데이터 손실**이었던 경우가 있었습니다. 빌드 성공은 정답이 아닙니다
- 방향을 잘못 잡으면 끝까지 갑니다. 범위를 좁혀 지시하는 편이 안전했습니다
- 배포 설정처럼 저장소 권한이 필요한 일은 결국 사람 손이 필요합니다

블로그를 AI로 관리한다는 건 글을 대신 써주는 것보다, **이런 유지보수를 대신 처리해주는 것**에 가깝습니다. 운영 비용이 거의 없어야 글을 계속 쓰게 되니까요.
